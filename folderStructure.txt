# Android Expense Tracker App — Architecture & Folder Structure Guide

# Overview

This document explains the complete folder structure, architecture, and purpose of every major section inside the Android Expense Tracker application.
---

# High-Level Architecture

The project is divided into multiple layers.

Each layer has a specific responsibility.

Main layers:

1. core/
2. data/
3. domain/
4. features/
5. ui/
6. navigation/
7. utils/

---

# 1. core/

Purpose:
The foundation of the app.

Contains app-wide systems and low-level functionality used throughout the application.

---

# core/database/

Purpose:
Handles all database setup and configuration.

Responsibilities:

* creating database
* managing database version
* defining database tables
* migrations
* database initialization

Example:
When app starts, database is initialized here.

---

# core/database/dao/

Purpose:
Database operation layer.

DAO = Data Access Object.

Responsibilities:

* insert transaction
* delete transaction
* update category
* fetch reports
* search records

Example:
Fetching all expenses from the last 30 days.

---

# core/database/entities/

Purpose:
Defines database table structures.

Responsibilities:

* transaction table structure
* category table structure
* tags table structure
* settings table structure

Example:
Defines fields like:

* amount
* category
* date
* notes

---

# core/database/converters/

Purpose:
Converts complex data types into database-friendly formats.

Example:
Converting:

* Date → timestamp
* Enum → integer/string

---

# core/database/migrations/

Purpose:
Handles database upgrades safely.

Example:
If app version 1 had no tags and version 2 introduces tags, migrations update the database without deleting old data.

---

# core/encryption/

Purpose:
Handles security and encryption.

Responsibilities:

* encrypting database
* securing backups
* password protection
* secure storage

Example:
Encrypt exported backup files.

---

# core/preferences/

Purpose:
Stores lightweight app settings.

Responsibilities:

* dark mode
* selected currency
* app preferences
* user settings

Example:
Saving the selected app theme.

---

# core/theme/

Purpose:
Controls app appearance.

Responsibilities:

* colors
* gradients
* typography
* fonts
* neon styling

Example:
Managing the dark neon UI theme.

---

# core/security/

Purpose:
Handles app protection.

Responsibilities:

* fingerprint unlock
* biometric authentication
* session management
* app lock

Example:
Fingerprint unlock before opening app.

---

# core/backup/

Purpose:
Backup and restore management.

Responsibilities:

* export database
* import backup
* restore old data
* backup scheduling

Example:
Creating a backup.db file.

---

# core/analytics/

Purpose:
Analytics calculation engine.

Responsibilities:

* category totals
* monthly reports
* spending trends
* dashboard calculations

Example:
Calculating total food expenses for current month.

---

# 2. data/

Purpose:
Handles data flow between database and business logic.

Acts as a bridge between:

* database
* repositories
* business layer

---

# data/model/

Purpose:
Raw data objects.

Responsibilities:
Representing data retrieved from storage.

Example:
TransactionModel contains:

* amount
* category
* transaction date

---

# data/mapper/

Purpose:
Transforms data between layers.

Responsibilities:
Converting database objects into UI/business-friendly objects.

Example:
Database transaction → dashboard transaction card model.

---

# data/repository/

Purpose:
Central data manager.

Responsibilities:

* fetching data
* updating data
* caching
* deciding data source

Example:
Dashboard requests all expenses.
Repository fetches them from database.

---

# 3. domain/

Purpose:
Contains pure business logic.

This layer does not contain Android UI code.

Acts as the brain of the application.

---

# domain/model/

Purpose:
Business-level models.

Represents clean app objects used across logic.

Example:
Transaction business object.

---

# domain/repository/

Purpose:
Defines repository contracts.

Responsibilities:
Defines what repositories must provide.

Example:

* add transaction
* delete transaction
* fetch reports

---

# domain/usecase/

Purpose:
Handles single app actions.

Each use case performs one business operation.

Examples:

* Add transaction
* Delete transaction
* Generate monthly report
* Calculate category totals

These are essentially app operations.

---

# Final Architecture Understanding

The app is divided into clear responsibilities:

| Layer      | Responsibility      |
| ---------- | ------------------- |
| core       | foundation systems  |
| data       | data management     |
| domain     | business logic      |
| features   | app screens/modules |
| ui         | reusable visuals    |
| navigation | screen movement     |
| utils      | helper utilities    |

---

# Recommended Design Philosophy

The project should remain:

* feature-based
* modular
* scalable
* analytics-focused
* secure
* easy to maintain

This structure is ideal for medium-to-large Android applications and will scale very well as the expense tracker grows in complexity.
